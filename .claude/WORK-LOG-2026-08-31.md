## 1. SWMS photos vanished from submissions

**Reported:** photos attached to a SWMS hazard row never appeared in the form submission view.

Two independent bugs, one behind the other.

### 1a. The field name was malformed (`e6027262` and earlier, `26440044`)

`slReindexRepeatFileInputs` rebuilds each hazard row's file-input name on every submit. It did:

```js
var match = fi.name.match(/^(answers_file\[\d+\])\[\d+(\]\[\])$/);
fi.name = match[1] + '[' + idx + ']' + match[2];   // match[2] is "][]"
```

`match[2]` already contains the closing bracket, and the replacement wrote another one, so
`answers_file[215686][0][]` went out as **`answers_file[215686][0]][]`**.

PHP's multipart parser does not truncate that name — it **discards the file entirely**:

| Field name | `$_FILES` |
|---|---|
| `answers_file[215686][0][]` | `{answers_file: {215686: [["row0.png"]]}}` |
| `answers_file[215686][0]][]` | `[]` — empty |

Because PHP drops it rather than raising `UPLOAD_ERR_*`, `storeFormUpload()` never reported
anything and the visitor saw a clean "submitted successfully". Hit the first row *and* every
"+ Add another" row, on mobile capture and desktop browse alike.

Second defect found alongside: `slReindexRepeatFileInputs(wrap)` was a no-op, because
`querySelectorAll` never matches the root element and `wrap` *is* the `[data-sl-repeat]`.

### 1b. Row alignment collapsed (`da6b3fbe`, test in `bd99c1d6`)

Once names were well formed, photos arrived but all landed on hazard #1.
`accumulateSwmsFileBucket()` recurses one level: the outer key is the row, the inner key is
the file's position *within* that row. The inner branch let the key win over the row index
passed down, and with one photo per row the inner key is always `0`:

```
one photo per row  [0=>[a], 1=>[b]]   →  row0=[a.jpg,b.jpg]     ← the reported symptom
three rows                            →  row0=[a,b,c]
```

Fixed so an explicit `$rowIndex` from the parent always wins.

**Why the tests didn't catch it:** all three existing tests asserted the *original filename*
appeared in the stored path, but `store()` always randomises it — the assertions could never
pass and died before reaching the row-alignment check. Rewritten to identify each row's photo
by byte size (distinct fixture dimensions), which actually verifies targeting.

**Verified:** red→green on the real suite — 3 failures on `a0950830`, `OK (4 tests, 42
assertions)` after. Field names confirmed in a live browser on staging.

## 2. Participant list — "Upload does nothing" (`bd99c1d6`, `cbd2c076`)

Three causes, two of them introduced by the first fix attempt.

1. **No feedback mechanism existed.** `layouts/participant-list-embed.blade.php` never
   rendered Filament's notifications component, so every `Notification::make()->send()` was
   dispatched into the void. Same page, `$this->js('alert(...)')` worked — which is why "Add"
   reported errors and "Upload" never did.
2. **Upload with no file chosen → total silence.** `$this->validate()` threw a
   `ValidationException` the embed has nowhere to render. Measured: `visibleError: null,
   errorNodes: 0, anyNotification: false`.
3. **A random .xlsx imported junk** — a `Qty` column of `12`/`3` read as Excel serial dates,
   creating participants due `11/01/1900`.

**First fix added `@livewire('notifications')` — that was wrong.** Filament's notification
styles are not part of that standalone layout, so it rendered as a giant unstyled icon
stacked under the table. Also switched the file input to `wire:model`, which uploads on
*change*, so the field flashed "uploading" and cleared itself before Upload was pressed.

**Final shape:** no `wire:model` — the input stays plain (keeps the filename), and the button
transfers + imports in one action via `$wire.upload()`. All messages go through the popup's
themed dialog. Dates before 2000 rejected; result distinguishes "N added", "N added, M
skipped", "Nothing imported".

**Verified in the browser against the live component:** selecting a file issues **no**
requests; clicking Upload shows "Uploading…", imports (3 rows → 5), clears the input; empty
click reports "Choose an .xlsx file first." and sends nothing.

**Employer / company column:** not a bug. It is never typed in the popup — legacy's
`update_participant_status()` stamps `employer_cmp` when someone *submits the form* through a
Participant Name question (type 18) with "include employer" enabled. `markParticipatedParticipants()`
mirrors this exactly, including inserting a walk-up participant who wasn't on the list.

## 3. Upload preview × button, and deleted videos (`11d1f55b`, `5ecb8a93`)

**× button:** measured in the live editor — `.sl-logo-upload` put it at `right:9px` while the
pictures repeater put it at `left:6.75px`. FilePond defaults the button to the left. Pinned
right for every upload preview in the profile editor.

**Deleted videos lingering in the form:** worse than cosmetic. The Videos repeater stores only
`title` + `video_name`, and saving re-syncs it back to the `video` table — so a video deleted
from the library was **recreated on the next save**.

First fix rewrote `$this->data` and **did not work**. Proven in the browser:

```
state after   ["video "]            ← correct
DOM after     ["video 4", "video"]  ← unchanged, even after a full $refresh
```

A Filament Repeater renders from child schemas it caches; only `rawState()` on the component
flushes them. Redone to do exactly what Filament's own delete action does — `rawState()`,
`callAfterStateUpdated()`, `partiallyRender()` — confirmed against that built-in action
(DOM `["video 4","video"]` → `["video"]`). Second lookup needed `withHidden: true`, since
"Videos #2" only renders for exhibit codes.

**Honest note recorded in the test file:** PHPUnit cannot cover this. The broken version
passed every assertion, including two written specifically to catch it, because Livewire's
test harness rebuilds child schemas from state on each access.

## 4. Date picker + sub-user "Add a New Code" (`33739c0f`)

**Selected date invisible.** flatpickr appends its calendar to `<body>`, outside `.sl-plist`
where the palette is declared, so `background: var(--sl-green)` was invalid-at-computed-value
time and dropped, while `color:#fff` still applied. Measured: `background rgba(0,0,0,0)`,
`color rgb(255,255,255)` — white on white. Palette redeclared on `.flatpickr-calendar`, day
colours stated literally.

**Sub-user 404.** A sub-user sees only profiles in `show_code_profile_id_to_acc_user` plus
open slots stamped with their own `user_id`. Reusing a session draft went through
`scrubIfPollutedCreateDraft()` — the one claim path that never stamped `user_id` — so a slot
owned by whoever bought the codes stayed invisible and record resolution 404'd.

Two more found because the existing test file used a blind `EquipmentType::factory()` insert
that violated the now-seeded unique `slag`, erroring before either assertion:

- **403 for an entitled sub-user** — `CreateProfile` extends `EditRecord`, so Filament
  authorised it with `canEdit()` (needs `access_edit`). Now `canCreate()`.
- **500 instead of 403** when unentitled — the bail-out left `$record` uninitialised.

## 5. Photo size on mobile, and dark mode (`6dd7d123`)

**Uploads.** Staging reported PHP's compiled-in 2MB limit, i.e. it is **not loading
`docker/php/conf.d/zz-performance.ini`** (which sets 32M/64M). Raising a server limit a
visitor on site cannot reach does not help, so photos are now resized in the browser before
being sent — 2560px long edge, JPEG q0.85, on both camera capture and browse.

Measured on a 4032×3024 fixture: **927 KB → 258 KB (72% smaller)** at 2560×1920. Files under
1MB and non-photos pass through; a re-encode that comes out larger is discarded; an
undecodable image submits as the original rather than being lost.

**Dark mode.** A contrast audit measured every element (parsing only `rgb()`/`rgba()` and
compositing alpha properly — a first pass mis-read Filament's `oklch()` tokens and produced
5 phantom findings).

| | Before | After |
|---|---|---|
| Submission view — title | 3.53:1 | 9.29:1 |
| Submission view — meta lines | 3.35:1 | 6.38:1 |
| Submission view — section label | 3.67:1 | 6.99:1 |
| Editor — QR URL block | **1.40:1** | 14.33:1 |
| Editor — amber note | 2.50:1 | 10.63:1 |
| Editor — doc/video links | 3.20:1 | 8.42:1 |
| Editor — activation note | 3.89:1 | 7.84:1 |
| Editor — share links | 4.06:1 | 10.18:1 |

Root cause on the submission view: the existing dark block only overrode the presenter's
*inline* colours, so everything driven by a CSS class kept its light-theme colour.

## 6. VOCC lifecycle parity (`efe8b25d`)

Mapped the whole VOCC lifecycle against the legacy Kohana app (`controller/voc.php` 1,606
lines, `voclogin.php`, `dashboard.php`, `cron.php`, `mailsend.php`, `model/voc.php`) and
closed four gaps.

1. **Imported card photos never displayed.** Legacy keeps them in `voc_profile_image`; the
   rebuilt editor reads `picture`, and nothing read the legacy table. Added the model,
   relation, card rendering — and the migration the table never had, which is part of why it
   was overlooked. `is_temp=1` rows stay hidden (legacy stages unconfirmed uploads that way).
2. **Card holders were not confined.** Legacy checks `voc_user_id` at the top of every
   dashboard action. The rebuild admitted `UserType::Voc` to the whole portal panel, with only
   the profiles list blocked as a side effect of having no client membership.
   `ConfineVocCardHolder` restores the rule as an allowlist.
3. **`/voclogin` redirected to the marketing home.** Legacy had a dedicated branded sign-in —
   the address printed on cards. Restored as a real page.
4. **Expiry notices matched an exact date,** so one missed scheduler run dropped that day's
   cohort permanently. Now a window, with `voc_document_notifications` making it idempotent.
   Marking only happens once mail actually goes out.

`--since` and `--dry-run` added: legacy sent **no** VOCC expiry mail at all, and all 12
imported documents are already expired (newest 2022-06-01), so an unguarded first run would
mail years of history.

A subtlety worth keeping: the first dedupe attempt still double-sent, because the model casts
`expiry_date` to a date (stored `Y-m-d 00:00:00`) while the marker held `Y-m-d`. Both sides
are now normalised with `date()`.

**12 tests, all green.** Gap analysis published as an artifact:
https://claude.ai/code/artifact/bbdbca66-cb56-4865-a7e2-8ac212cff53c
